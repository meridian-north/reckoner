Support and feedback

Support address selected by the maintainer: meridian.north@pm.me. Response times are not guaranteed.

For a reproducible software problem or suggestion, use this repository’s Issues tab. Include browser/version, the step, expected result and actual result. Use synthetic examples. Never attach personal, confidential or regulated records, credentials, private keys, or an unreviewed export. GitHub attachments may upload immediately.

For a suspected vulnerability or sensitive report, email the support address first with a minimal description and ask for a suitable transfer method. Do not place sensitive details in public Issues or ordinary email. This project does not currently offer a verified encrypted reporting channel.

Names and roles in review records are self-declared. Support does not provide legal advice, institutional approval, account recovery or preservation guarantees. Keep originals and exported backups independently.

Before reporting a save or reopen problem

- Keep the original source file and the JSON history backup separately. Do not clear browser/site data as a first troubleshooting step.
- Record the browser and OS version, the exact button and message, and whether a JSON file appeared in Downloads. A requested download is not proof of completed delivery.
- If the app offers unsaved-draft recovery, download it privately before replacing or reopening work. Use one editing tab per workspace.
- Try reproducing the software issue with the bundled synthetic example or permitted court demo. Do not send the full source, private workload list or your unreviewed history bundle to support.

Accessibility reports

Include the blocked task, browser/OS, keyboard or assistive technology used, and the control label or focus problem. Native Safari keyboard/accessibility-tree checks are scoped evidence. Complete VoiceOver speech and current physical-device acceptance remain unverified; keyboard access remains in scope. User feedback on the compact layout does not establish every accessibility task. Screenshots should be cropped and checked for private text, account details and unrelated windows before sending.

Support scope

Support handles software behavior and suggestions. A source correction is a proposed contribution for its host, not a support-approved ruling. Neither email nor a local review automatically submits it to Internet Archive or another institution. Public Issues are suitable only for public-safe software reports after the release repository is available; sensitive reports start with a minimal non-sensitive email description. Mailbox monitoring and response times are operational responsibilities, not verified delivery guarantees.

Which file should I keep?

Choose Save reading below the reading fields to store a revision locally. Header Save to file (or More → Save to file) exports the resumable creator history. More → Export contribution receipt exports the latest readable receipt, which is not the full recovery bundle. Keep original source files and hOCR separately. Choose Open saved review in the header, or find it under More on narrow screens, to select an exported history file. Your files · save & reopen under More → Tools & guidance offers a separate-workspace route and explains the possible confirmations. A standalone receipt can be refused when the browser retains creator history for the same record; use its history backup rather than clearing site data.

On wider screens Save has its own row below the scrolling fields. A validation message should leave it visible. On a narrow screen the form flows down the page; a successful save returns the comparison into view. New file starts a separate workspace without deleting the previous one. For prepared batches, use More → Open a review pack and select its contents list (MODULE.json) and extracted source folder. A refused type, size, encoding or fingerprint does not authorize changing source bytes to force a match.

The main form’s readings CSV is an index, not the experimental WAL. The optional WAL workbench preserves its own CSV, receipt snapshots and previous WAL bytes in a separate archive. Retain independently saved checkpoints if you want to check rollback; a hash shown inside an imported file is not an independent checkpoint.

Troubleshooting without losing work

| What you see | What to do next |
| --- | --- |
| “Save this reading before selecting another word…” | Stay on the current passage. Save the proposal with its reason, or deliberately restore the untouched values if you intend to skip. Download draft recovery before closing if saving fails. Do not reload to bypass the warning. |
| The source or hOCR hash does not match | Keep the current record and reopen the exact retained source image and original hOCR. A resized, recompressed or rescanned image is a different file. Do not change the receipt hash or claim correspondence just to restore a highlight. |
| Duplicate/oversized page identity or duplicate word identity | Keep the supplied hOCR unchanged. Ask its producer for uniquely identified pages/words, or retain a readable JSON proposal without claiming a successful hOCR import. A manually repaired copy is a separate derivative. |
| A standalone receipt is refused because creator history already exists | Use that record’s history backup. Keep both copies independently; do not clear site data to discard the retained checkpoint. Use Merge only for supported related records, not to force unrelated histories together. |
| Save succeeds but no file appears | Save stores locally; it is not a disk export. Request Save to file and check the browser’s Downloads list and destination. Keep the tab open until you have verified the file. |
| hOCR export requires well-formed XHTML | Keep the original and use the readable contribution JSON. Import/display compatibility does not guarantee a derivative can be safely produced. Do not overwrite the supplied hOCR. |
